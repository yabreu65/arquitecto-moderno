# Capitulo 12 - Seguridad y Observabilidad Enterprise

## Contexto

En clientes enterprise, seguridad y auditoria no son extras.
Son condiciones minimas para vender, operar y renovar contratos.

En este nivel, la pregunta no es "tenemos auth?".
La pregunta real es:
- podemos reconstruir exactamente que paso?
- podemos probar aislamiento por tenant?
- podemos demostrar cumplimiento ante auditoria externa?

Sin eso, el producto queda fuera de deals grandes aunque funcione tecnicamente.

## Que aprendera el lector

- Audit logging por tenant.
- Cifrado de datos en reposo.
- Enfoque de cumplimiento sin matar productividad.
- Como definir eventos auditables con valor legal y operativo.
- Como equilibrar seguridad, performance y costo.

## Introduccion tecnica

Un sistema auditado debe poder responder que paso, quien lo hizo,
cuando ocurrio y bajo que contexto de tenant.

Seguridad enterprise no es una feature unica.
Es una arquitectura de controles:
- preventivos (acceso, cifrado)
- detectivos (logs, alertas)
- correctivos (respuesta a incidentes)

Si una sola capa falla, las otras tienen que sostener trazabilidad.

## Alcance y limites

Este capitulo cubre:
- controles de seguridad y auditoria por tenant
- cifrado, compliance y respuesta ante incidentes
- observabilidad tenant-aware para seguridad y FinOps

Este capitulo no cubre:
- diseno profundo de contratos async y compensaciones (ver Capitulo 22)
- operacion SRE formal con error budgets (ver Capitulo 21)

## Audit logging por tenant

### Que debe registrar un evento auditable

Minimo recomendado:
- `tenant_id`
- `actor` (`sub` o service account)
- accion
- recurso afectado
- timestamp
- resultado (success/failure)
- `trace_id` o correlacion

Sin estos campos, el log sirve para mirar, no para investigar.

### Que operaciones auditar primero

Prioridad alta:
- cambios de permisos/roles
- acceso a datos sensibles
- configuraciones de seguridad
- acciones administrativas
- operaciones financieras

No todo evento debe ser audit log.
Pero todo evento de alto impacto debe serlo.

## Tenant isolation con Postgres RLS

RLS en Postgres permite imponer aislamiento en capa de datos.

Regla de oro:
- toda tabla tenant-scoped con politica RLS explicita
- sesion de DB con contexto seguro de `tenant_id`

Esto agrega defensa en profundidad:
si una query en aplicacion olvida filtro, RLS puede bloquear el acceso cruzado.

## Cifrado de datos en reposo

### Cifrado en DB y storage

Niveles habituales:
- cifrado de volumen/disco
- cifrado de backups
- cifrado de objetos en storage

Para datos sensibles:
- considerar cifrado de campo o tokenizacion

### Gestion de llaves

Error clasico: cifrar bien y gestionar claves mal.

Buenas practicas:
- usar KMS/HSM gestionado
- rotacion periodica de keys
- control estricto de acceso a material criptografico

## Cumplimiento (compliance) pragmatico

No conviertas compliance en burocracia infinita.
Transformalo en controles concretos medibles.

Ejemplos:
- retencion de logs con politica definida
- segregacion de ambientes
- acceso privilegiado con aprobacion
- evidencias automatizadas de controles

Si todo depende de procesos manuales, escala mal y falla en auditoria real.

## Deteccion y respuesta

Audit logs sin alertas son historico, no defensa activa.

Necesitas:
- reglas de deteccion de eventos sospechosos
- alertas por patron (accesos anormales, cambios masivos)
- playbooks de incidente

Tiempo de deteccion y tiempo de respuesta importan tanto como prevenir.

## NUEVO 12.3 - Observabilidad tenant-aware con OpenTelemetry

La observabilidad tradicional (CPU, memoria, latencia media por servicio) no alcanza en SaaS multi-tenant.
Los promedios mienten.

Si el 99% de tenants responde en 100ms pero tu tenant premium cae a 5s, la plataforma puede "verse sana" y aun asi estar fallando donde mas duele el negocio.

### Pilar 1: trazabilidad con contexto propagado

OpenTelemetry debe unificar trazas, metricas y logs en todos los servicios.

Regla operativa:
- cada request de entrada genera `trace_id`
- el `tenant_id` viaja como contexto (baggage/atributos)
- la correlacion se mantiene en API, workers, colas y DB

`trace_id` y correlacion no son lo mismo:
- `trace_id` sigue el arbol tecnico de una peticion
- `correlation_id` conecta eventos de negocio y workflows cruzados

Para soporte enterprise, ambos deben convivir.

### Pilar 2: metricas RED y USE por tenant

No midas solo API global.
Medi por tenant con tags:

- RED: requests, errors, duration por `tenant_id`
- USE: utilizacion, saturacion y errores por recurso compartido

Esto permite responder preguntas reales:
- que tenant esta degradado ahora?
- que release afecto a que segmento?
- donde esta el cuello: app, DB, queue o worker?

### Pilar 3: deteccion del noisy neighbor

Noisy neighbor = tenant que consume recursos desproporcionados y degrada a los demas.

Deteccion:
- latencia p95/p99 por tenant
- consumo de DB por `tenant_id`
- jobs por tenant en cola

Mitigacion automatizable:
- rate limits por tenant
- circuit breakers segmentados
- throttling de reportes pesados

Sin observabilidad tenant-aware, esta mitigacion llega tarde.

### Implementacion en NestJS (interceptor de telemetria)

```ts
import { CallHandler, ExecutionContext, Injectable, NestInterceptor } from "@nestjs/common";
import { Observable } from "rxjs";
import { context, propagation, trace } from "@opentelemetry/api";

@Injectable()
export class TenantTelemetryInterceptor implements NestInterceptor {
  intercept(contextRef: ExecutionContext, next: CallHandler): Observable<unknown> {
    const request = contextRef.switchToHttp().getRequest();
    const tenantId = request.user?.tenantId ?? request.headers["x-tenant-id"] ?? "anonymous";
    const activeSpan = trace.getActiveSpan();

    if (activeSpan) {
      activeSpan.setAttribute("tenant.id", tenantId);
      activeSpan.setAttribute("http.method", request.method);
      activeSpan.setAttribute("http.route", request.route?.path ?? "unknown");
    }

    const baggage = propagation.createBaggage({
      "tenant.id": { value: String(tenantId) },
    });

    return context.with(propagation.setBaggage(context.active(), baggage), () => next.handle());
  }
}
```

Importante: el `tenant_id` ideal viene de contexto autenticado (JWT/tenant context), no solo de headers sin validar.

### FinOps: costo por tenant

Observabilidad no es solo incident response.
Tambien es economia de plataforma.

Al etiquetar por `tenant_id`:
- queries de DB
- mensajes de cola
- ejecuciones de workers
- llamadas a IA/terceros

podes estimar costo real por tenant y proteger margen.

Guardrails recomendados:
- presupuesto de costo por tenant
- alertas de desviacion
- politicas de throttling por plan

### Criterio del arquitecto senior

La observabilidad tenant-aware es el sistema nervioso del SaaS.
No la uses solo para errores.
Taggea tambien exito, latencia y consumo por tenant.

Solo asi podes cumplir SLOs enterprise por cliente y no por promedio global.

## Trade-offs y criterios de decision

### Trade-off 1: detalle de auditoria vs costo/ruido

Loggear todo puede saturar costo y analisis.
Loggear poco deja ciegos los incidentes.

Criterio:
- auditar por impacto de negocio y riesgo regulatorio.

### Trade-off 2: cifrado profundo vs latencia operativa

Mas cifrado puede subir latencia/complejidad.

Criterio:
- priorizar cifrado fuerte en datos sensibles y rutas de mayor riesgo.

### Trade-off 3: compliance manual vs compliance automatizado

Manual arranca rapido.
Automatizado escala y reduce errores humanos.

Criterio:
- automatizar controles repetibles desde etapas tempranas.

## Errores comunes (y por que pasan)

- Auditoria sin `tenant_id` o sin actor identificable.
- Logs sin integridad ni retencion definida.
- Claves criptograficas en variables sin control de ciclo de vida.
- Cumplimiento tratado solo como documento, no como controles.
- Falta de playbooks para incidentes de seguridad.

La causa frecuente: seguridad vista como "checklist de venta" y no como capacidad de plataforma.
