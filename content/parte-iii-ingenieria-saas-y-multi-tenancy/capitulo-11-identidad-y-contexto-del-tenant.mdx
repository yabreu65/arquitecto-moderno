# Capitulo 11 - Identidad y Contexto del Tenant

## Contexto

En multi-tenancy, la identidad del usuario no alcanza.
Hay que resolver tambien el contexto de tenant en cada request.

Este punto parece obvio hasta que aparecen incidentes:
- usuario valido operando sobre datos de otro tenant
- jobs asincronos sin contexto correcto
- trazas sin informacion de tenant para investigar

La pregunta no es solo "quien llama".
La pregunta completa es:
- quien
- para que tenant
- con que permisos
- desde que canal

## Que aprendera el lector

- Resolucion de tenant ID por subdominio, ruta y headers.
- Inyeccion de tenant context en servicios NestJS.
- Validaciones para evitar contaminacion cruzada.
- Patrones de propagacion de contexto en flujos sync y async.
- Riesgos al mezclar contexto de usuario y contexto de tenant.

## Introduccion tecnica

El tenant context debe ser explicito, trazable y consistente.
Si queda implicito, aparecen bugs silenciosos y brechas de seguridad.

Arquitectura robusta define una "fuente de verdad" para resolver tenant y la aplica de manera uniforme.
No se permite que cada modulo "adivine" tenant con reglas propias.

## Alcance y limites

Este capitulo cubre:
- resolucion de tenant y normalizacion de tenant context
- inyeccion en NestJS para evitar parameter pollution
- gatekeeper API para bloqueo temprano de acceso cruzado

Este capitulo no cubre:
- decisiones de topologia de datos (ver Capitulo 10)
- politicas de compliance y auditoria profunda (ver Capitulo 12)

Objetivo senior:
- dominio ciego a la mecanica multi-tenant
- infraestructura con inyeccion automatica de contexto
- bloqueo temprano de acceso cruzado antes de tocar datos

## Que es el tenant context

El tenant context es un objeto por request que encapsula identidad operativa.
No es un detalle cosmico: es un contrato de seguridad y trazabilidad.

Responsabilidad:
- ser unica fuente de verdad durante el ciclo de vida de la peticion
- evitar que cada capa pase `tenant_id` manualmente

Contrato minimo recomendado:
- `tenant_id`
- `user_id`
- `plan_tier`
- `permissions` (RBAC/ABAC)
- `trace_id` (si hay observabilidad distribuida)

Si este contrato no existe, el sistema cae en parameter pollution y decisiones inconsistentes.

## Resolucion de tenant ID

Antes de inyectar contexto, hay que resolver tenant de forma confiable en el borde.
Una plataforma madura suele combinar entradas, pero con normalizacion interna unica.

Matriz practica:

| Estrategia | Mecanismo | Caso de uso |
| --- | --- | --- |
| Subdomain-based | `tenant1.buildingos.com` | SaaS B2B con branding y separacion por cliente |
| Header-based | `X-Tenant-Id: <id>` | APIs internas/BFF con gateway confiable |
| JWT claims | claim `org.id` o `tenant_id` firmado | Estandar moderno para identidad verificable |

Regla de seguridad:
- si `tenant_id` viene por header externo sin control de borde, NO confiarlo ciegamente.

### Estrategia por subdominio

Ejemplo:
- `acme.tuapp.com` -> `tenant_id = acme`

Ventajas:
- claro para UX y operacion
- facil de enrutar en gateway

Riesgos:
- validacion insuficiente de dominio
- edge cases en entornos internos o custom domains

### Estrategia por verified domains

En entornos enterprise, muchos clientes exigen dominio propio (`docs.cliente.com`).
Para sostener seguridad y gobernanza:

- registrar dominio verificado por tenant
- validar ownership criptograficamente (DNS/TXT)
- mapear dominio -> `tenant_id` en control plane

Beneficio:
- onboarding enterprise robusto
- menor riesgo de suplantacion por dominio

### Estrategia por path

Ejemplo:
- `/t/acme/reports`

Ventajas:
- simple para entornos sin DNS por tenant

Riesgos:
- mayor posibilidad de manipular tenant en URL sin controles fuertes

### Estrategia por headers

Ejemplo:
- `X-Tenant-Id: acme`

Ventajas:
- util en BFFs y APIs internas

Riesgos:
- alta confianza en origen del header
- requiere gateway que sanee/controle encabezados

Regla:
- si el tenant viene por header desde cliente externo sin control de borde, el riesgo sube fuerte.

## Inyeccion de tenant context en NestJS

Patron recomendado:
1. middleware o guard resuelve tenant
2. valida pertenencia usuario-tenant
3. guarda `tenant context` en request scope
4. servicios consumen contexto tipado, no strings sueltos

Esto reduce errores de propagacion y estandariza auditoria.

### Inyeccion implicita para evitar parameter pollution

El objetivo es no pasar `tenant_id` por cinco capas a mano.
En NestJS, request-scoped providers permiten encapsular esto sin ensuciar casos de uso.

```ts
import { Injectable, Scope } from "@nestjs/common";

@Injectable({ scope: Scope.REQUEST })
export class TenantContext {
  tenantId!: string;
  userId!: string;
  planTier?: string;
  permissions: string[] = [];

  setContext(input: {
    tenantId: string;
    userId: string;
    planTier?: string;
    permissions?: string[];
  }) {
    this.tenantId = input.tenantId;
    this.userId = input.userId;
    this.planTier = input.planTier;
    this.permissions = input.permissions ?? [];
  }
}
```

```ts
@Injectable()
export class PrismaPropertyRepository implements IPropertyRepository {
  constructor(
    private readonly prisma: PrismaService,
    private readonly context: TenantContext,
  ) {}

  async findMany() {
    return this.prisma.property.findMany({
      where: { tenantId: this.context.tenantId },
    });
  }
}
```

El filtro tenant vive en adaptadores de infraestructura, no en dominio.

## Gatekeeper en la capa API

El gatekeeper valida identidad y contexto antes de que la request llegue a DB o IA.
Es la frontera donde se ejecutan politicas de aislamiento.

Controles minimos:
- comparar tenant del request con tenant firmado en JWT
- validar pertenencia usuario-tenant y permisos efectivos
- bloquear tenant suspendido o fuera de policy
- registrar auditoria con `tenant_id`, `user_id`, `trace_id`

Resultado:
- si hay mismatch de tenant, la peticion muere en borde
- no hay chance de contaminacion cruzada por error de repositorio

### Verified domains para onboarding enterprise

Para clientes enterprise, el dominio corporativo ayuda a automatizar alta de tenant:
- validas ownership via DNS/TXT
- mapeas dominio -> `tenant_id` en control plane
- asignas tenant correcto en login sin pasos manuales frágiles

## Propagacion en flujos asincronos

No alcanza con request HTTP.
Tambien hay que propagar contexto en:
- eventos
- colas
- workers
- tareas programadas

Regla practica:
- todo job/evento tenant-scoped lleva `tenant_id` obligatorio en payload.

Si no, un worker puede ejecutar con contexto incompleto y afectar otro tenant.

## Contratos de seguridad para tenant context

Validaciones minimas:
- usuario pertenece al tenant activo
- rol/permisos validos para ese tenant
- token no expirado/revocado
- tenant activo (no suspendido)

Estas validaciones deben vivir en fronteras de entrada, no dispersas aleatoriamente.

## Trade-offs y criterios de decision

### Trade-off 1: resolver tenant temprano vs flexibilidad por modulo

Resolver tenant en borde estandariza.
Resolver en cada modulo da flexibilidad aparente.

Criterio:
- resolver temprano y propagar contexto tipado.

### Trade-off 2: request-scoped context vs simplicidad de performance

Request scope facilita consistencia.
Puede tener costo de performance si se usa sin criterio.

Criterio:
- usar request scope en rutas tenant-criticas y medir impacto.

Alternativa para alto trafico:
- `AsyncLocalStorage` de Node.js permite propagar contexto por cadena async
- reduce overhead de providers request-scoped en algunos perfiles de carga

Regla practica:
- empezar por request scope por claridad arquitectonica
- migrar a `AsyncLocalStorage` cuando tengas evidencia de cuello real en profiling

### Trade-off 3: una unica estrategia de resolucion vs estrategia hibrida

Una estrategia unica simplifica.
Hibrida puede ser necesaria por canales distintos.

Criterio:
- permitir multiples entradas, una sola normalizacion interna.

## Errores comunes (y por que pasan)

- Confiar `tenant_id` enviado por cliente sin validacion cruzada.
- Resolver tenant en controller y olvidar en jobs asincronos.
- Mezclar contexto de sesion global con contexto tenant local.
- No loggear `tenant_id` en operaciones criticas.
- No testear escenarios de acceso cruzado.

La causa mas frecuente es no tratar tenant context como contrato de seguridad.
