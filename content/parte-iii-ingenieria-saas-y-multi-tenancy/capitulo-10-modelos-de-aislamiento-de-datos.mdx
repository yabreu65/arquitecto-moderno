# Capitulo 10 - Modelos de Aislamiento de Datos

## Contexto

El modelo de aislamiento de datos es una de las decisiones mas caras de corregir en un SaaS B2B.
Define seguridad, costo operativo, rendimiento, cumplimiento y velocidad de evolucion.

Cuando se elige por intuicion y no por criterios, aparecen sintomas predecibles:
- ruido entre tenants
- consultas complejas para filtrar contexto
- migraciones lentas
- costos de infraestructura impredecibles

No existe un modelo perfecto universal.
Existe un modelo adecuado para tu etapa de producto, perfil de cliente y postura de riesgo.

## Que aprendera el lector

- Comparativa de modelos de aislamiento por tenant.
- Tradeoffs de costo, seguridad y operacion.
- Implementacion de Postgres RLS.
- Criterios para cambiar de modelo sin colapsar el producto.
- Riesgos mas comunes de leakage multi-tenant.

## Introduccion tecnica

No existe modelo perfecto universal. El objetivo es elegir el modelo correcto
para la etapa del producto y el perfil de clientes.

En la practica, la decision suele moverse entre tres enfoques:
- `database-per-tenant`
- `schema-per-tenant`
- `shared-tables` con `tenant_id`

Cada uno optimiza algo distinto.
Arquitectura madura explicita que prioriza y que sacrifica.

## Modelo 1: database-per-tenant

### Que ofrece

Cada tenant vive en una base separada.
Es el maximo aislamiento logico y operativo.

Ventajas:
- separacion fuerte de datos
- cumplimiento mas facil en clientes exigentes
- menor riesgo de leakage por query incorrecta

Costos:
- operacion mas compleja (miles de DBs)
- upgrades y migraciones mas pesadas
- costo de infraestructura creciente

Uso recomendado:
- clientes enterprise de alto valor con exigencias regulatorias estrictas.

## Modelo 2: schema-per-tenant

### Que ofrece

Una misma base, varios schemas.
Da aislamiento razonable con menor costo que database-per-tenant.

Ventajas:
- buen balance entre aislamiento y operacion
- backup/restore por tenant mas viable
- menor costo base

Costos:
- tooling de migraciones mas cuidadoso
- crecimiento de objetos por schema
- complejidad en observabilidad por tenant

Uso recomendado:
- etapa intermedia con necesidad de aislamiento superior a shared-tables.

## Modelo 3: shared-tables con tenant_id

### Que ofrece

Todos los tenants comparten tablas y se segmenta por `tenant_id`.
Es el modelo mas comun para etapas iniciales y escalado rapido.

Ventajas:
- simplicidad de operacion
- migraciones unificadas
- costo inicial mas bajo

Costos:
- mayor riesgo de leakage por errores de filtrado
- ruido de rendimiento entre tenants
- compliance mas desafiante para ciertos segmentos

Uso recomendado:
- producto temprano o mid-market con fuerte foco en velocidad.

## Postgres RLS (Row Level Security)

RLS permite reforzar aislamiento en capa de base, no solo en aplicacion.

Beneficio clave:
- incluso si una query olvida filtro, politica RLS puede bloquear acceso fuera del tenant.

Regla arquitectonica:
- RLS no reemplaza buenos filtros en app
- RLS agrega defensa en profundidad

Minimos para usarlo bien:
- politica por tabla tenant-scoped
- contexto de sesion confiable (`tenant_id`)
- pruebas automticas de acceso cruzado

## Estrategia de evolucion entre modelos

No te cases dogmaticamente con el primer modelo.
Diseña desde el inicio para evolucionar.

Patron pragmatico:
1. arrancar con shared-tables bien gobernado
2. mover tenants premium a schema-per-tenant o database-per-tenant cuando negocio lo requiera
3. mantener abstraccion de acceso que permita coexistencia temporal

La clave es tener contratos de datos que no asuman una sola topologia para siempre.

## NUEVO 10.4 - Estrategia de particionado hibrido y control plane

La evolucion enterprise rara vez termina en un modelo unico.
Lo habitual es una estrategia hibrida donde conviven topologias por segmento de tenant.

En terminos practicos:
- tenants SMB pueden vivir en `pool` (shared-tables)
- tenants growth pueden migrar a `schema-per-tenant`
- tenants premium/regulados pueden operar en `silo` (database-per-tenant)

El desafio no es tecnico solamente.
Es operativo: decidir, registrar y automatizar en que topologia vive cada tenant en cada etapa.

El control plane define:
- en que topologia vive cada tenant
- reglas de promocion entre tiers
- politicas de capacidad, backup y cumplimiento
- automatizacion de provisiones y migraciones

Sin control plane, una estrategia hibrida se vuelve operativamente caotica.

Capacidades minimas del control plane:
- registro maestro de tenants y su topologia activa
- flujos de migracion idempotentes
- auditoria de cambios de topologia
- observabilidad de estado por tenant

### Flujo de promocion entre topologias

Un flujo recomendado para evitar migraciones traumaticas:
1. detectar umbral de negocio/tecnico (volumen, compliance, noisy-neighbor)
2. crear destino (`schema` o `database`) para el tenant
3. replicar y validar datos
4. ejecutar cutover controlado
5. monitorear integridad y latencia post-cutover

Si no hay este flujo, la estrategia hibrida se transforma en operaciones manuales con alto riesgo.

### Tenant catalog como fuente de verdad

El control plane necesita un catalogo de tenants con, al menos:
- `tenant_id`
- topologia activa (`pool`/`schema`/`silo`)
- version de esquema
- endpoint de datos asociado
- politicas de retencion/compliance

La API y los workers deben enrutar por este catalogo, no por reglas hardcodeadas.

### Guardrails para particionado hibrido

Minimos operativos:
- plantillas IaC por topologia
- runbooks de rollback de migracion
- pruebas de no-contaminacion multi-tenant
- alertas por drift entre catalogo y recursos reales

Sin guardrails, el modelo hibrido pierde trazabilidad y se vuelve dificil de auditar.

## Trade-offs y criterios de decision

### Trade-off 1: aislamiento maximo vs costo operativo

Mas aislamiento reduce riesgo.
Tambien sube costo de operacion.

Criterio:
- segmentar tenants por criticidad y valor, no aplicar misma topologia a todos.

### Trade-off 2: simplicidad inicial vs deuda de seguridad

Shared-tables acelera salida.
Sin guardrails, aumenta riesgo de leakage.

Criterio:
- si usas shared-tables, `tenant_id` + RLS + testing obligatorio.

### Trade-off 3: un solo modelo global vs estrategia hibrida

Un modelo unico simplifica mental model.
Estrategia hibrida mejora fit por segmento.

Criterio:
- hibrido cuando hay segmentos enterprise y SMB con necesidades distintas.

## Errores comunes (y por que pasan)

- Elegir modelo por moda de arquitectura.
- No incorporar `tenant_id` en indices claves.
- Confiar solo en filtros de aplicacion sin RLS ni pruebas.
- No planear migracion entre modelos.
- Ignorar impacto de "noisy neighbor" en tenants grandes.

La causa central es evitar decisiones explicitas de aislamiento temprano.

- [ ] Existe politica de segmentacion de tenants.

- [ ] Se evalua RLS para tablas criticas.
- [ ] Hay pruebas de no-contaminacion entre tenants.
- [ ] Se monitorea ruido de rendimiento entre tenants.
- [ ] Estrategia de migracion entre modelos esta definida.
- [ ] Costos por modelo se revisan periodicamente.
