# Capitulo 16 - Multi-tenant RAG

## Contexto

RAG multi-tenant no es solo indexar documentos.
Es garantizar aislamiento semantico y seguridad entre clientes.

En IA aplicada a SaaS B2B, el peor incidente no es una respuesta floja.
Es responder con informacion correcta del tenant equivocado.

Ese riesgo aumenta cuando el equipo piensa RAG solo como "buscar embeddings".
RAG multi-tenant es un problema de arquitectura de datos, seguridad y trazabilidad.

## Que aprendera el lector

- Arquitecturas Silo, Pool y Bridge para datos vectoriales.
- Uso de Pinecone y PGVector en contextos multi-tenant.
- Riesgos de fuga de conocimiento entre tenants.
- Como definir filtros de retrieval por `tenant_id`.
- Como evaluar leakage y precision por tenant.

## Introduccion tecnica

La capa de retrieval define que contexto ve el modelo.
Si esa capa falla, el sistema puede responder datos de otro cliente.

RAG tiene tres zonas sensibles:
- ingestion
- indexing
- retrieval

Si cualquiera de esas zonas pierde aislamiento, el prompt final queda contaminado.

## Alcance y limites

Este capitulo cubre:
- aislamiento de datos vectoriales en contexto multi-tenant
- autorizacion en retrieval con pre-filtering
- evaluacion de leakage y calidad por tenant

Este capitulo no cubre:
- diseno de flujos multi-agente (ver Capitulo 17)
- gobernanza runtime y cuotas operativas de agentes (ver Capitulo 18)

## Prerequisitos

- Entender aislamiento y tenant context en SaaS (Capitulos 10 y 11).
- Comprender fundamentos de seguridad y auditoria por tenant (Capitulo 12).

## Output esperado

- Diseñar retrieval multi-tenant con pre-filtering.
- Definir postura de aislamiento vectorial por segmento.

## 16.1 Aislamiento en bases de datos vectoriales

El desafio principal no es la similitud semantica.
Es garantizar que cada consulta vea solo conocimiento autorizado por `tenant_id`.

Dos estrategias base:
- `namespaces` o indices dedicados por tenant (aislamiento logico fuerte)
- indice compartido con metadata filtering estricto por `tenant_id`

Regla:
- namespaces suelen encajar mejor en tenants premium/enterprise
- metadata filtering reduce costo pero exige disciplina total en filtros y auditoria

### Silo

Cada tenant tiene su propio indice o namespace dedicado fuerte.

Ventajas:
- maximo aislamiento
- debugging y auditoria mas claros

Costos:
- mayor costo de operacion
- mayor fragmentacion de datos

### Pool

Todos comparten infraestructura vectorial con filtrado por metadatos (`tenant_id`).

Ventajas:
- eficiencia de costo
- operacion mas simple

Costos:
- riesgo elevado si filtros fallan
- mayor dependencia de gobernanza estricta

### Bridge

Modelo hibrido: pool para base general + silo para tenants criticos o sensibles.

Ventajas:
- balance entre costo y aislamiento

Costos:
- complejidad de routing y gobernanza

## Pinecone y PGVector (criterio de uso)

Pinecone:
- servicio gestionado, rapido para escalar
- buen soporte de namespaces y operaciones vectoriales

PGVector:
- control total en ecosistema Postgres
- integracion fuerte con stack SQL existente

Criterio:
- velocidad de adopcion y managed ops -> Pinecone
- control infra y proximidad a datos relacionales -> PGVector

No es batalla de herramientas.
Es alineacion con tu contexto operativo.

## 16.2 Pipeline de autorizacion de IA

Reglas minimas:
- filtro obligatorio por `tenant_id`
- metadatos inmutables del documento
- validacion cruzada del contexto antes de construir prompt

Principio operativo:
- `pre-filtering` obligatorio en retrieval enterprise
- `post-filtering` solo como defensa secundaria y monitoreada

Patron recomendado:
1. resolver `tenant context`
2. resolver permisos efectivos del actor (RBAC/ABAC)
3. ejecutar retrieval scopeado por tenant y `doc_id` permitido
4. auditar ids de chunks recuperados
5. construir prompt con trazabilidad de fuentes

## NUEVO 16.3 - Gobernanza y autorizacion en IA: pre-filtering vs post-filtering

En un pipeline RAG tradicional, el motor vectorial optimiza similitud semantica, no autorizacion.
Como arquitectos, tenemos que imponer acceso antes de que los datos lleguen al LLM.

### Aislamiento vectorial: base de la gobernanza

Antes de discutir filtros, definimos donde viven los vectores:

- `Silo` (namespace o indice por tenant): maximo aislamiento, recomendado para tenants premium.
- `Pool` (indice compartido + metadata): mas eficiente en costo, pero con mayor disciplina de filtros.
- `Bridge` (hibrido): pool para base general, silo para segmentos sensibles.

La estrategia de filtrado hereda el riesgo del modelo de aislamiento.

### Estrategia A: Pre-filtering (estandar enterprise)

El sistema decide que documentos puede ver el actor antes de consultar el vector store.

Flujo tecnico:
1. Usuario envía consulta.
2. Servicio RBAC/ABAC resuelve permisos por `tenant_id`.
3. Se construye filtro estricto por metadata (`tenant_id`, `doc_id`, `status`, etc.).
4. Se consulta vector DB con ese filtro desde el inicio.

Ejemplo conceptual:

```ts
query(vector, {
  filter: {
    tenant_id: "org_123",
    doc_id: { $in: allowedIds },
    status: "published",
  },
});
```

Problema que resuelve:
- el motor no "mira" vectores prohibidos, reduciendo riesgo de fuga en retrieval.

Trade-off:
- mayor carga inicial cuando el set permitido es muy grande.

### Estrategia B: Post-filtering (rapida pero riesgosa)

La busqueda se ejecuta primero y el filtrado de autorizacion se aplica despues.

Flujo tecnico:
1. Recuperas top-K por similitud sin contexto fuerte.
2. En capa de aplicacion descartas resultados no autorizados.

Riesgo critico:
- over-fetching: los top-K pueden venir de otros tenants y dejar respuesta vacia o sesgada aunque existan datos validos.

Regla de arquitectura:
- no usar post-filtering como barrera principal en multi-tenant enterprise.
- si se usa, que sea capa secundaria con monitoreo y pruebas de leakage.

### Patron Gatekeeper API para BuildingOS

No permitimos que el orquestador de IA consulte directo al vector store.
Definimos una capa Gatekeeper que centraliza:

- autenticacion y autorizacion
- inyeccion de `tenant_id`
- politicas de filtrado
- trazabilidad (`trace_id`, fuentes y decisiones)

Ventaja:
- si cambiamos de Pinecone a PGVector, la gobernanza no cambia.

### Implementacion de referencia en NestJS (Interceptor)

```ts
import {
  CallHandler,
  ExecutionContext,
  Injectable,
  NestInterceptor,
} from "@nestjs/common";
import { Observable } from "rxjs";

@Injectable()
export class RagSecurityInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    const request = context.switchToHttp().getRequest();
    const tenantId = request.user.tenantId;

    request.body.vectorFilter = {
      tenant_id: tenantId,
      status: "published",
    };

    return next.handle();
  }
}
```

El objetivo no es confiar en que el servicio de IA "se acuerde" de filtrar.
El objetivo es forzar controles de seguridad por defecto.

### Tabla comparativa

| Caracteristica | Pre-filtering | Post-filtering |
| --- | --- | --- |
| Seguridad | Alta: datos no autorizados no se recuperan | Baja: riesgo de leakage y vacios |
| Latencia | Mayor costo inicial en retrieval | Menor retrieval, mayor descarte app |
| Uso en SaaS | Recomendado/obligatorio en enterprise | Solo casos internos acotados |
| Complejidad | Mayor coordinacion de metadatos/permisos | Mas simple de implementar |

Criterio de arquitecto senior:
- tratar embeddings como datos sensibles;
- reforzar aislamiento en motor (silo o RLS/metadata estricta) y en aplicacion (pre-filtering + gatekeeper).

## Evaluacion de calidad y leakage

No alcanza con medir "respuesta correcta".
Debes medir tambien:
- precision por tenant
- recall por tenant
- tasa de leakage inter-tenant

Pruebas recomendadas:
- datasets sinteticos cruzados
- red-team prompts para intentar exfiltracion
- suites regression por tenant sensible

## Trade-offs y criterios de decision

### Trade-off 1: costo de infraestructura vs riesgo de leakage

Pool reduce costo.
Silo reduce riesgo.

Criterio:
- segmentar por criticidad de tenant y requerimiento regulatorio.

### Trade-off 2: contexto amplio vs latencia/costo

Mas contexto puede mejorar calidad.
Tambien sube latencia y costo token.

Criterio:
- retrieval orientado a relevancia, no a cantidad.

### Trade-off 3: velocidad de prototipo vs gobernanza de datos

Prototipar RAG es rapido.
Gobernar lifecycle de documentos no.

Criterio:
- definir ownership de ingestion, borrado y reindex desde inicio.

## Errores comunes (y por que pasan)

- Filtrado por tenant solo en app, no en motor vectorial.
- Metadatos incompletos en chunks.
- No poder rastrear documentos fuente de una respuesta.
- No tener estrategia de borrado por tenant (right to forget).
- Evaluar solo calidad linguistica y no seguridad.

La causa habitual: tratar RAG como feature de UX en lugar de subsistema critico.
