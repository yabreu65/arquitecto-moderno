# Capitulo 15 - Infraestructura y Ciclo de Vida

## Contexto

Escalar SaaS no es solo agregar pods.
Es operar de forma consistente el ciclo de vida completo de cada tenant.

En entornos enterprise, el riesgo no esta solo en caidas.
Tambien esta en procesos manuales de provison, cambios de plan, migraciones y offboarding.

Si ese ciclo depende de operaciones artesanales, la plataforma no escala aunque el codigo este bien.

## Que aprendera el lector

- Como modelar tenant lifecycle como flujo operativo automatizable.
- Diferencia entre control plane y data plane para operaciones SaaS.
- Como usar IaC para provisionar infraestructura reproducible.
- Como aplicar Terraform/CDK en onboarding y offboarding de tenants.
- Que guardrails necesita una plataforma para evitar drift operativo.

## Introduccion tecnica

Infraestructura moderna para SaaS debe tratarse como codigo.
No como conjunto de clicks en consola.

IaC permite:
- repetibilidad
- auditoria de cambios
- rollback controlado
- consistencia entre entornos

Sin IaC, cada tenant se vuelve una excepcion.

## Tenant lifecycle como arquitectura

Estados tipicos:
- `requested`
- `provisioning`
- `active`
- `suspended`
- `offboarding`
- `archived`

Cada transicion debe tener validaciones, eventos y ownership.

Si no defines estados, el soporte y operaciones trabajan a ciegas.

## Control plane vs data plane

Control plane:
- decide y orquesta estados del tenant
- gestiona configuracion, planes y politicas

Data plane:
- ejecuta trafico y operaciones funcionales del producto

Separar estos planos reduce acoplamiento y mejora gobernanza.

## IaC en SaaS enterprise

IaC no es opcional cuando el negocio exige trazabilidad y velocidad.

Casos concretos:
- provision de recursos por tenant tier
- gestion de secretos por entorno
- networking y politicas de acceso
- observabilidad base por stack

Regla:
- todo cambio estructural debe pasar por version control y review.

## NUEVO 15.3 - Automatizacion del Tenant Lifecycle con IaC (Terraform/CDK)

### El problema: el abismo de la configuracion manual

Cuando crece el nivel de aislamiento (silo o estrategia hibrida), la operacion manual explota.

Onboarding manual implica crear a mano:
- bucket de documentos
- recursos de datos
- namespaces vectoriales
- secretos y permisos

Consecuencias:
- drift por diferencias entre tenants
- fallos impredecibles por permisos incompletos
- costo oculto de recursos huerfanos
- riesgo de incumplimiento en offboarding

### Arquitectura del control plane de aprovisionamiento

El control plane orquesta herramientas de IaC segun eventos de negocio.

Flujo tecnico recomendado:
1. billing confirma alta/pago de tenant
2. backend publica evento de provisioning
3. worker o runner ejecuta stack IaC parametrizado con `tenant_id`
4. al finalizar, registra endpoints y secretos en tenant catalog
5. data plane enruta trafico segun esa configuracion

Esto convierte eventos de negocio en cambios reales de infraestructura, de forma auditable.

### Terraform vs CDK (criterio de seleccion)

| Caracteristica | Terraform (HCL) | CDK/Pulumi (TypeScript) |
| --- | --- | --- |
| Paradigma | Declarativo (estado deseado) | Imperativo (codigo) |
| Ventaja principal | Estandar de mercado, multi-cloud | Mismo lenguaje que backend NestJS |
| Mejor fit | Stacks estables y repetibles | Logica condicional compleja |
| Riesgo tipico | Abstracciones complejas en modulos | Acoplar demasiado IaC con app code |

Regla de arquitecto:
- elegi por skill del equipo y modelo operativo, no por hype.

### Implementacion conceptual en BuildingOS (CDK)

```ts
import * as s3 from "aws-cdk-lib/aws-s3";
import { RemovalPolicy, Stack, Tags } from "aws-cdk-lib";
import { Construct } from "constructs";

export class TenantInfrastructureStack extends Stack {
  constructor(scope: Construct, id: string, props: { tenantId: string }) {
    super(scope, id);

    const bucket = new s3.Bucket(this, `TenantBucket-${props.tenantId}`, {
      encryption: s3.BucketEncryption.S3_MANAGED,
      removalPolicy: RemovalPolicy.RETAIN,
      autoDeleteObjects: false,
    });

    Tags.of(bucket).add("TenantID", props.tenantId);
  }
}
```

La idea no es el bucket en si.
La idea es que todo recurso quede trazable y gobernado por `tenant_id`.

### Offboarding seguro y limpieza automatica

Offboarding no es solo "dar de baja usuario".
Es ejecutar una politica de lifecycle:
1. revocar accesos y secretos
2. aplicar retencion temporal segun compliance
3. destruir recursos elegibles via IaC
4. registrar evidencia de cierre

Si esto no es automatico, aparecen costos zombie y riesgos legales.

## Guardrails operativos

Minimos para evitar drift:
- policy checks en CI
- naming conventions estandar
- tagging obligatorio por tenant y entorno
- deteccion de drift periodica
- runbooks de rollback

Sin guardrails, IaC tambien puede degradarse.

## SLOs operativos para lifecycle

Tambien conviene definir SLOs del plano operativo:
- tiempo maximo de onboarding de tenant
- tasa de exito de pipelines IaC
- tiempo de remediacion de drift
- tiempo de offboarding completo

Sin SLOs, la operacion escala por percepcion y no por evidencia.

### Criterio del arquitecto senior

No automatices por moda.
Con pocos tenants, cierto nivel manual puede ser aceptable.
Pero si el objetivo es escalar a long-tail enterprise, la automatizacion del tenant lifecycle define margen y velocidad.

Meta practica:
- acercar el costo marginal de onboarding a cero horas de ingenieria manual.

## Trade-offs y criterios de decision

### Trade-off 1: automatizacion total vs complejidad inicial

Automatizar todo al inicio puede ser excesivo.
Automatizar nada bloquea crecimiento.

Criterio:
- automatizar primero caminos repetitivos de mayor riesgo operativo.

### Trade-off 2: Terraform vs CDK

Terraform:
- ecosistema amplio y estandar de mercado

CDK:
- expresividad en lenguajes de programacion

Criterio:
- elegir por habilidades del equipo y stack de proveedores.

### Trade-off 3: velocidad de onboarding vs controles de cumplimiento

Onboarding muy rapido sin validaciones aumenta riesgo.

Criterio:
- gates de seguridad/compliance en pipeline de provision.

## Errores comunes (y por que pasan)

- Provision manual fuera de IaC.
- No modelar estados del tenant explícitamente.
- No limpiar recursos en offboarding.
- Falta de tagging por tenant.
- Ausencia de deteccion de drift.

La causa tipica es tratar operaciones como soporte y no como parte de arquitectura.
